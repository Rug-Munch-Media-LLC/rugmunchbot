# RugMunchBot Audit Report — 2026-08-27

**Scope:** Full audit of `/srv/work/repos/rugmunchbot` (1089 tests, 593 files, 144K lines)
**Goal:** Identify gaps between bot and RAG/scanner, dysfunctional output, missing features, quality issues.

---

## 🔴 CRITICAL ISSUES

### 1. RAG Connection Gaps
**Finding:** The bot's RAG connection is vendored and relies on `_vendor/rag_pkg/` which is a frozen copy.
- `scan_memory.py` indexes scans to Qdrant but the bot has no way to verify if RAG is available
- `should_index_scan()` gates indexing but failures are silent (fail-open contract)
- No health check for RAG/Qdrant connectivity at startup

**Impact:** Scans may not be indexed into RAG memory, causing "have we scanned this token before?" queries to return no results.

### 2. Broken Backend API Contracts
**Finding:** TODO.md documents 3 broken backend API calls (now superseded but worth verifying):
- `/api/v1/databus/wallet/{address}` → 404 (only `/wallet/{address}/tokens` + `/pnl` exist)
- `/api/v1/databus/cross_chain/{address}` → 404
- `/api/v1/scanner/webhooks/register` → 404

**Impact:** Wallet forensics, cross-chain tracing, and webhook registration may silently fail.

### 3. Silent Exception Swallowing
**Finding:** Multiple `except Exception: pass` blocks in vendored code:
- `_vendor/unified_scanner/_finalize_helpers.py` — now fixed (warning-tier logging)
- `_vendor/news_ingest/discovery.py` — silent failures
- `_vendor/news_ingest/ingest.py` — silent failures

**Impact:** Data ingestion issues are invisible to operators.

## 🟠 HIGH PRIORITY ISSUES

### 4. Webhook Delivery Gaps
**Finding:** The webhook system lacks:
- No retry mechanism for failed deliveries (single attempt only)
- No dead letter queue for failed events
- No batch delivery for high-frequency events
- No signature verification for incoming webhook tests
- No delivery metrics tracking

**Impact:** Webhook subscribers may miss events silently.

### 5. Tool Registry Error Handling
**Finding:** Tools return `ok=False` on failure but callers may not always handle this gracefully.
- Some tools return `None` instead of `ToolResult(ok=False)`
- No global timeout for tool execution chain
- ToolResult.error is optional and may be empty

**Impact:** Users see "no live data" when they should see specific error context.

### 6. Scan Output Quality
**Finding:** The scan output formatters are fragmented across multiple files:
- `_scan_report_main.py`, `_scan_report_common/`, `_scan_report_deepscan/`, etc.
- Risk scores may not be normalized across v1/v2/sentinel scan types
- Some fields may be `None` instead of "Not Available" in user-facing output

**Impact:** Inconsistent user experience across scan types.
